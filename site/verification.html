Verification

Not a PPT. Run it yourself.

The premise is proven by four tiers of reproducible verification. Everything below is one command and one shell session away — no trust required.

The one command

Reproducible offline verification of every tier this page describes (where the tooling is available on the host): 

node scripts/verify.mjs

That single script drives the Python suite, the offline TS E2E, the real-child runtime E2E, and the generated-package E2E — and, when a real dsh monorepo checkout is present, the REAL-composition and strict typecheck tiers too.

The four tiers

1 · Python suite 43 tests

Covers the decorators end-to-end, PEP 484 → JSON Schema type inference, the JSON-RPC runtime, and a real Python subprocess integration test over stdio. 

cd python/sdk-dsl && PYTHONPATH=src python3 -m pytest tests/
# → 43 passed in 1.6s

2 · Offline TypeScript E2E 55+ assertions

Plain-Node assertions with no package install. Covers codegen emission, runtime lifecycle (worker-exit, reconnect, teardown ladder, env scrub), a real python3 child round-trip, and a generated package mounted on a stub Cordis context. 

node scripts/verify.mjs   # runs the offline tier
# → ALL OK · codegen/runtime/lifecycle/real-child/generated-package

3 · REAL-composition real Cordis

A test cordis.yml booted through the genuine vendored Cordis Loader (vendor/loader + vendor/include): real schemastery applying the generated static Config, the real ToolRuntime holding the registered tool, a real ctx.emit('session/event') reaching the Python listener, and ctx.fiber.dispose() tearing the child down through the effect disposers. 

scripts/setup-integration.mjs   # one-time
node tests/integration/real-composition.mjs
# → plugin loaded · tool registered · event delivered · child disposed

4 · Strict typecheck 0 errors

tsc -b over the two bridge packages and a generated example package, inside the monorepo's project-reference graph. TypeScript 6.0.3 with the monorepo tsconfig.base.json flags: strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes. 

scripts/typecheck-integration.mjs
# → tsc -b : 0 errors

Honest limits

Everything above is real, and it's the strongest evidence available without running in your specific environment. Before you rely on the bridge, you should also know what it doesn't (yet) do:

  • The parser is regex-based. "Any Python module" means the constrained decorator shape: keyword-argument decorators with one leading positional name (@service(name='ml', ...)). Qualified calls (@dsh_bridge.service(...)), import aliases (from dsh_bridge import service as svc), and non-keyword arguments are silently ignored. Only the first @service class per module is emitted; non-dataclass __init__ parameters are not introspected.
  • Five decorators are parsed but not yet emitted. @capability, @method, @guard, @restrict_tools, and @system_prompt_section appear in the IR but produce no generated code today. See Roadmap for the sequence they're being added in.
  • Vitest suites in the standalone repo are unrun. The vitest configurations under packages/bridge/*/tests/ depend on a vitest closure that isn't available offline. Their assertions are mirrored by the plain-Node E2E scripts in tests/e2e/ and run for real inside the monorepo.
  • Monorepo integration is verified, not merged. The deepseek-harness checkout holds the bridge packages plus a tsconfig.base.json paths registration as uncommitted working-tree changes from the verification run — they're reproducible from this repo, but they aren't a PR into deepseek-ai/deepseek-harness yet.
