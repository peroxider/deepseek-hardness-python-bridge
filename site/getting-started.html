Get started

Three steps to a native dsh plugin.

Most of the work is in the first step — annotating your Python with the decorators that declare which capabilities you want to expose. The next two steps are mechanical.

Step 1. Decorate

Pick a Python module you already have. Add a few decorators to mark the class that should become a service, the function that should become a model-visible tool, and the listener you want to attach to events. Business logic doesn't move. 

from dataclasses import dataclass
from dsh_bridge import provide_method, service, tool, on

@service(name="ml")
@dataclass
class MLProvider:
    """A stateful service — instantiated once per session, lives in ctx.ml."""
    model_path: str

    @provide_method(timeout_ms=10_000)
    def embed(self, texts: list[str]) -> list[list[float]]:
        # Your existing implementation, untouched.
        return self._model.encode(texts)

@tool(name="shout", description="Upper-case a string.",
      parameters={"text": {"type": "string"}})
def shout(text: str) -> dict:
    # Tools are stateless; bridge wraps as ctx.tools.register(defineTool(...)).
    return {"text": text.upper()}

@on("session/event", mode="emit")
def audit(event: str, payload: dict) -> None:
    # Listeners run on every emitted event of the matching namespace.
    log_to_siem(event, payload)

A few details worth noting:

  • Decorators return the original callable unchanged. Without a bridge attached, this module imports and runs as plain Python.
  • @dataclass on a @service lets the bridge forward cordis.yml's initArgs into __init__ by field name — type-checked at the Python layer.
  • Type hints matter. They're inferred (PEP 484) and become the JSON Schema the model sees for @tool parameters and the TypeScript types on @provide_method return values.

Step 2. Generate or Install

Pick the path that fits your situation.

Manual — when you want every artifact on disk

Run the codegen, then tsc it, then assemble the plugin directory yourself. Good for monorepos where the bridge packages live as workspace members. 

# Generate the TypeScript bridge package
pnpm dsh-bridge-codegen src/my_ml/provider.py \
  --out  packages/@my-org/python-bridge-ml \
  --name @my-org/python-bridge-ml

# Build it (strict tsc)
pnpm --filter @my-org/python-bridge-ml build

Then wire it in cordis.yml like any other plugin (Step 3).

One-shot — when you're packaging for an existing dsh install

For a development-stage dsh install that can't load .ts source directly. One command runs codegen → build → assemble → smoke → patch, with each step leaving artifacts the next one consumes. 

scripts/install-python-plugin.py \
  --source     path/to/bridge.py \
  --name       '@my-org/lkb-bridge' \
  --module     lkb_dsh.bridge \
  --python-src path/to/my-python/src \
  --config-json '{"boardId": "my-board"}'

Installer flags

Every flag accepted by scripts/install-python-plugin.py:

--source
Path to the decorated Python entry module. Required.
--name
Plugin package name (e.g. @my-org/lkb-bridge). Required.
--module
Dotted Python module path to import in the child runtime. Required.
--python-src
Repeatable. Path(s) to your Python source tree to bundle into the self-contained plugin dir.
--plugin-dir
Where to assemble the plugin (default: derived from --name).
--id
Plugin id used in cordis.yml (default: derived from --name).
--profile
dsh install profile to patch (default: web).
--python-bin
Python interpreter the child process spawns (default: python3).
--config-json
JSON object merged into the plugin's cordis.yml config: block (default: {}).
--steps
Comma-separated subset to run (default: codegen,build,assemble,smoke,patch).
--uninstall
Reverse patch (and optionally --delete-dir).
--delete-dir
With --uninstall, also remove the plugin directory.
--dry-run
Print the would-be patch without writing anything.

Environment overrides for non-standard machines: DSH_TSC, DSH_NODE, DSH_MONOREPO, DSH_INSTALL, DSH_HOME, DSH_TYPE_ROOTS. The script falls back to dsh-bundled js-yaml if PyYAML is absent, and to copying where symlinks are denied.

Step 3. Wire it in cordis.yml

dsh-bridge plugins are first-class in cordis.yml — same schema as a hand-written TS plugin, plus a small config: block the bridge runtime reads. 

- id: ml
  name: '@my-org/python-bridge-ml'
  config:
    pythonBin: python           # interpreter for the child process
    module: my_ml.provider      # dotted path to your decorated module
    className: MLProvider       # @service class to instantiate
    sandbox: workspace-write    # dsh-side policy (NOT a bridge requirement)
    modelPath: /opt/models/embeddings.npy   # forwarded as initArgs to MLProvider.__init__

What every config key means

pythonBin
The interpreter invoked as the child process. python, python3, or an absolute path. The child runs python -u -m dsh_bridge.runtime <module>.
module
Dotted import path the child process loads. Anything importable in the bundled python-src tree works.
className
Name of the @service class to instantiate as the long-lived service. Omit if you only expose tools/listeners.
sandbox
dsh policy — not interpreted by the bridge. Use the same values you'd use for a TS plugin.
any other key
Forwarded as keyword args to the dataclass __init__ by field name (e.g. modelPath → model_path).

Sanity check. Confirm the child is alive

After dsh boots, the bridge runtime stays resident as a Python child process. You can see it from another terminal: 

ps aux | grep dsh_bridge.runtime
# → python -u -m dsh_bridge.runtime my_ml.provider

If you can see the child, the JSON-RPC channel is open: the shout tool is registered with ctx.tools, the session/event listener is attached, and MLProvider.embed is reachable from any other plugin via ctx.ml.embed(...).
